# 10 — مصفوفة التتبعية وحالات الحواف (Traceability & Edge Cases)

يربط هذا الملف كل جدول بعملية أعمال فعلية (لضمان عدم وجود جداول نظرية بلا استخدام)، ويوثّق حالات الحواف الحرجة في الوحدات الأكثر حساسية.

---

## 1. مصفوفة التتبعية: جدول ← عملية أعمال (Table → Business Flow)

القاعدة: **كل جدول له مُنتِج (Create) ومُستهلِك (Read/Report) وعملية تحكمه**. أي جدول بلا صف هنا = مرشّح للحذف.

### النواة والأمان
| الجدول | يُنشأ في (Producer) | يُستهلك في (Consumer) | العملية المحورية |
|--------|---------------------|------------------------|-------------------|
| branches | إعداد المكتب | فلترة كل الكيانات، تقارير الفروع | العزل التنظيمي |
| departments | الإدارة › الأقسام | ملف الموظف، تقارير القسم | الهيكل التنظيمي |
| users | الإدارة › المستخدمون | تسجيل الدخول، Audit | المصادقة |
| roles / permissions / role_permission / user_role | الإدارة › الأدوار | كل فحص صلاحية (Middleware/Policy) | التفويض |
| sessions | تسجيل الدخول | إدارة الجلسات، الخروج من كل الأجهزة | إدارة الجلسات |
| settings | الإعدادات | كل الوحدات (سياسات، ترقيم، قوالب) | ضبط النظام |

## 2. حالات الحواف (Edge Cases)

### 2.1 الحضور والانصراف
| الحالة | السلوك المطلوب |
|--------|-----------------|
| بصمة دخول بلا خروج (نسيان) | إغلاق افتراضي عند نهاية النوبة + تعليم `needs_review` + تنبيه؛ لا يُحتسب إضافي تلقائياً |
| بصمتان دخول متتاليتان | تُؤخذ الأولى كـ check_in وتُتجاهل النبضات ضمن نافذة (مثل 2 دقيقة) |
| خروج قبل دخول (خلل توقيت) | تُرفع للمراجعة اليدوية بدل الاحتساب الخاطئ |
| بصمة في يوم إجازة معتمدة | الحالة `leave` تسبق `present`؛ تُسجَّل البصمة لكن لا تُلغي الإجازة (تنبيه تعارض) |
| بصمة في عطلة/إجازة رسمية | تُحتسب كامل الوقت إضافياً حسب سياسة العمل في العطل |
| موظف يعمل عبر منتصف الليل (نوبة ليلية) | ربط الخروج باليوم الصحيح عبر منطق النوبة (Overnight Shift) |
| تعدد الأجهزة (دخول من جهاز، خروج من آخر) | التجميع على مستوى الموظف/اليوم عبر كل الأجهزة، لا لكل جهاز |
| بصمة لموظف مُنهى/موقوف | تُحفظ معلّقة + تنبيه (قد تدل على محاولة تلاعب) |
| فرق توقيت الجهاز عن الخادم | تخزين UTC + مزامنة NTP دورية + إزاحة معلومة لكل جهاز |
| تصحيح يدوي بأثر رجعي بعد إغلاق الشهر | ممنوع إن كان الشهر مُقفلاً محاسبياً؛ يتطلب فتح استثنائي معتمَد + Audit |

### 2.2 الإجازات
| الحالة | السلوك المطلوب |
|--------|-----------------|
| رصيد غير كافٍ | منع/تنبيه؛ السماح فقط عبر تجاوز معتمَد (بدون راتب) |
| تداخل مع إجازة أخرى معتمدة | رفض التداخل الزمني لنفس الموظف |
| إجازة تشمل عطلات/عطل رسمية | تُحتسب أيام العمل الفعلية فقط (استبعاد الويكند/العطل) |
| إلغاء إجازة معتمدة | إعادة الرصيد + تصحيح الحضور + Audit + إشعار |
| تعديل تواريخ بعد الاعتماد | يتطلب دورة موافقة جديدة وإعادة احتساب الرصيد |
| طلب يمتد عبر سنتين ماليتين | تقسيم الأيام على رصيد كل سنة |
| مدير الموظف هو مقدّم الطلب | تصعيد الاعتماد للمستوى الأعلى (Manager-of-Manager) |
| نوع يتطلب مرفقاً (مرضية) بلا مرفق | منع الإرسال حتى إرفاق المستند |

### 2.3 القضايا والجلسات
| الحالة | السلوك المطلوب |
|--------|-----------------|
| إغلاق قضية بجلسات مستقبلية مجدولة | تحذير + إلغاء/ترحيل الجلسات المعلّقة أولاً |
| تعارض جلستين لنفس المحامي بنفس الوقت | تنبيه تعارض في التقويم + اقتراح إعادة جدولة |
| ترحيل جلسة | إنشاء جلسة تالية آلياً وربطها بالسابقة (سلسلة) |
| نقل قضية لمحامٍ آخر | تحديث المسؤول + الحفاظ بالتاريخ + إشعار الطرفين + Audit |
| حكم نهائي مع مهلة استئناف | تنبيهات تنازلية قبل انتهاء المهلة؛ منع إغلاق نهائي قبلها اختيارياً |
| حذف عميل مرتبط بقضايا | ممنوع (RESTRICT)؛ أرشفة فقط |
| رقم قضية بالمحكمة مكرر لعميلين | مسموح (الفريد داخلياً `case_no` فقط)، مع تنبيه احتمال التكرار |
| مرفق سري في قضية | يخضع لـ `documents.view_confidential` حتى لأعضاء الفريق |

### 2.4 القيود المالية
| الحالة | السلوك المطلوب |
|--------|-----------------|
| تعديل/حذف قيد مرحّل (posted) | ممنوع؛ يُنشأ **قيد عكسي (Reversal)** فقط + Audit |
| قيد غير متوازن (مدين ≠ دائن) | رفض الحفظ (فحص إلزامي) |
| دفعة تتجاوز رصيد الفاتورة | منع، أو تسجيل الزائدة كـ **رصيد دائن للعميل (Credit)** حسب السياسة |
| دفعة بعملة مختلفة | تحويل بسعر الصرف المسجّل وقت الدفع + حفظ العملة الأصلية |
| إلغاء فاتورة مسدّدة جزئياً | منع؛ يلزم رد المدفوع (Refund) أولاً + قيد عكسي |
| صرف يتجاوز رصيد الصندوق | تحذير/منع حسب السياسة (منع السالب) |
| ازدواج تسجيل الدفعة (نقرة مزدوجة) | **Idempotency-Key** يمنع القيد المكرر |
| ضريبة على بند معفى | دعم نِسب ضريبة صفرية/إعفاء على مستوى البند |
| إغلاق شهر مالي ثم دفعة بتاريخ سابق | تُسجَّل في الفترة المفتوحة التالية أو تتطلب فتحاً معتمَداً |

## 3. مبدأ عام لمعالجة الحواف
- **الرفض الآمن (Fail-safe):** عند الالتباس، تُرفع الحالة للمراجعة البشرية بدل الاحتساب الخاطئ.
- **قابلية التدقيق:** كل استثناء/تجاوز يُسجَّل في `audit_logs` مع المبرِّر والمعتمِد.
- **عدم فقدان البيانات:** الطبقة الخام (Staging) تحفظ كل شيء حتى غير القابل للمعالجة فوراً.
- **الاختبار:** كل حالة حافة أعلاه تُقابلها حالة اختبار (Test Case) في [ملف 11](11-quality-and-operations.md).
