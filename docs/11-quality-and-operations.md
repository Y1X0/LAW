# 11 — الجودة والتشغيل (Performance, Testing, Migration & DR)

يعالج هذا الملف بالأرقام: أهداف الأداء، استراتيجية الاختبار، خطة ترحيل البيانات، وخطة الاستمرارية والتعافي من الكوارث.

## 1. أهداف الأداء (Performance Targets / SLOs)

### 1.1 زمن الاستجابة (Latency)
| نوع الطلب | الهدف P50 | الهدف P95 | الهدف P99 |
|-----------|:--------:|:--------:|:--------:|
| قراءة API بسيطة (سجل واحد) | < 100ms | < 300ms | < 600ms |
| قوائم مفلترة/مرقّمة | < 200ms | < 500ms | < 1s |
| كتابة/تحديث (Transaction) | < 250ms | < 600ms | < 1.2s |
| لوحة التحكم (KPIs مجمّعة) | < 300ms | < 800ms | < 1.5s |
| تقرير ثقيل (يُولَّد بالخلفية) | غير متزامن | إشعار عند الجهوزية | ≤ 60s للتوليد |
| استقبال Webhook بصمة | < 150ms | < 400ms | < 800ms |

### 1.2 السعة والتزامن (Capacity & Concurrency)
| المؤشر | المرحلة الحالية (10 موظفين) | هدف التوسع (500+ موظف / عدة فروع) |
|--------|:---------------------------:|:----------------------------------:|
| مستخدمون متزامنون (Concurrent) | 15–30 | 500–1,000 |
| طلبات/ثانية (RPS) | 20–50 | 500+ |
| اتصالات WebSocket المتزامنة | ~30 | 1,000+ |
| نبضات بصمة/دقيقة | ~20 | 5,000+ (عدة فروع) |
| توليد كشوف رواتب | 10 خلال < 5 دقائق | 1,000 خلال < 15 دقيقة (Batch) |

### 1.3 حجم البيانات المتوقع (Data Volume — 3 سنوات)
| الجدول | الحجم التقديري (10 موظفين) | الحجم عند التوسع |
|--------|:--------------------------:|:----------------:|
| attendance_logs | ~50K صف/سنة | ملايين → **Partition شهري** |
| attendance_records | ~3.6K صف/سنة | مئات الآلاف |
| audit_logs | ~200K صف/سنة | ملايين → **Partition شهري** |
| notifications | ~100K صف/سنة | ملايين → **Partition + أرشفة** |
| cases + documents | مئات → آلاف | عشرات الآلاف (S3 غير محدود) |
| journal_lines | آلاف/سنة | ملايين |

### 1.4 كيفية تحقيق الأهداف
- **فهرسة** كل FK والحقول كثيرة الفلترة/الفرز (موثّقة في [ملف 02](02-database-design.md)).
- **Caching (Redis):** مؤشرات لوحة التحكم، الإعدادات، الصلاحيات، القوائم المرجعية.
- **Materialized Views** للتقارير التجميعية + تحديث مجدول.
- **Read Replicas** لفصل حمل التقارير عن العمليات.
- **Partitioning** زمني للجداول عالية النمو.
- **Async/Queue** لكل عملية ثقيلة (PDF، Excel، إشعارات، مزامنة).
- **Pagination إجبارية** (لا استرجاع غير محدود) + **N+1 Query Prevention** (Eager Loading).
- **CDN + Gzip/Brotli** للأصول الثابتة، و**HTTP Caching** المناسب.

## 2. استراتيجية الاختبار (Testing Strategy)

هرم الاختبار (Testing Pyramid): قاعدة عريضة من اختبارات الوحدة، فأقل تكاملاً، فأقل E2E.

```
        /\        E2E / UI (قليلة، حرجة)
       /--\       Feature / API (متوسطة)
      /----\      Integration (تكامل الوحدات + DB)
     /------\     Unit Tests (كثيرة، سريعة)
```

### 2.1 أنواع الاختبار
| النوع | النطاق | أمثلة | الأداة المقترحة |
|-------|--------|-------|------------------|
| **Unit** | دوال/خدمات منعزلة | معادلة صافي الراتب، احتساب التأخير، توازن القيد | PHPUnit/Pest · Jest |
| **Integration** | خدمة + قاعدة بيانات/طابور | حفظ سجل بصمة → معالجته إلى attendance_records | PHPUnit + DB اختبار |
| **Feature/API** | Endpoint كامل + صلاحيات | `POST /leaves` مع رصيد كافٍ/غير كافٍ، فحص RBAC | Pest/PHPUnit HTTP |
| **Contract** | ثبات عقد الـ API | مطابقة مخطط OpenAPI | Dredd/Schemathesis |
| **E2E / UI** | تدفق المستخدم عبر الواجهة | تسجيل دخول → إنشاء قضية → جدولة جلسة | Playwright/Cypress |
| **Security** | ثغرات وصلاحيات | IDOR، SQLi، XSS، تجاوز صلاحية | OWASP ZAP + مراجعة |
| **Load/Stress** | الأداء تحت الحمل | 1,000 مستخدم متزامن، 5K بصمة/دقيقة | k6/JMeter/Locust |
| **UAT** | قبول المستخدم | سيناريوهات أعمال حقيقية مع المكتب | يدوي موثّق |

### 2.2 تغطية الحالات الحرجة (Test Cases من ملف 10)
كل حالة حافة في [ملف 10](10-traceability-and-edge-cases.md) لها حالة اختبار مقابلة، ومنها إلزامياً:
- بصمة دخول بلا خروج → إغلاق افتراضي + `needs_review`.
- طلب إجازة برصيد غير كافٍ → رفض.
- تعديل قيد مرحّل → منع + إتاحة قيد عكسي فقط.
- ازدواج دفعة (Idempotency) → قيد واحد فقط.
- وصول محامٍ لقضية ليست له → 403.
- إغلاق قضية بجلسات مستقبلية → تحذير/منع.

### 2.3 أهداف التغطية والجودة
- تغطية **≥ 80%** للمنطق الحرج (المالية، الرواتب، الحضور، الصلاحيات).
- تغطية **≥ 60%** إجمالاً.
- **بوابة جودة CI:** لا دمج قبل نجاح كل الاختبارات + فحص Lint/Static Analysis (PHPStan/ESLint) + مسح تبعيات (Dependabot/Snyk) + **مسح الأسرار (Secret Scanning)** عبر gitleaks/trufflehog على كل Push + التحقق من `.env` ضمن `.gitignore` (يُرفض أي سرّ مُسرَّب في الـ diff).
- **بيانات اختبار:** Factories/Seeders + بيئة اختبار ببيانات **مُقنّعة** (Masked) من الإنتاج.

### 2.4 خط CI/CD
```
Push/PR → Lint + Static Analysis → Unit + Integration → Feature/API →
Build → (Staging) Deploy → E2E + Load (دوري) → موافقة → (Production) Deploy
```

## 3. استراتيجية ترحيل البيانات (Migration Strategy)

### 3.1 هجرة المخطط (Schema Migrations)
- **Migrations مُصدَّرة** (Versioned) قابلة للتقديم/التراجع (up/down)، تعمل آلياً في كل بيئة عبر CI.
- **بدون توقف (Zero-downtime):** تغييرات متوافقة للخلف (إضافة عمود Nullable ثم ملء ثم فرض القيد) — نمط Expand/Contract.

### 3.2 استيراد البيانات القديمة (Legacy Data Import)
عند وجود بيانات سابقة (Excel/نظام قديم):
```mermaid
flowchart LR
    SRC["مصادر قديمة\n(Excel / نظام سابق)"] --> EXT["استخراج (Extract)"]
    EXT --> MAP["تخطيط الحقول (Mapping)"]
    MAP --> CLN["تنظيف + تحقق (Validate/Clean)"]
    CLN --> STG[("جداول Staging")]
    STG --> DRY["تشغيل تجريبي (Dry-run)\n+ تقرير أخطاء"]
    DRY --> LOAD["تحميل نهائي (Load) في بيئة الإنتاج"]
    LOAD --> REC["تسوية وتحقق (Reconciliation)"]
```
- **قوالب استيراد (Excel Templates)** للموظفين/العملاء/القضايا/الأرصدة الافتتاحية.
- **التحقق قبل التحميل:** الرقم الوطني الفريد، توازن الأرصدة الافتتاحية، سلامة العلاقات.
- **Dry-run إلزامي** يُنتج تقرير أخطاء قبل التحميل الفعلي.
- **تسوية بعدية:** مطابقة الإجماليات (عدد الموظفين، أرصدة الصناديق) بين القديم والجديد.

### 3.3 الإطلاق التدريجي (Phased Rollout)
| المرحلة | النطاق | الهدف |
|---------|--------|-------|
| Pilot | وحدة HR + الحضور فقط لفرع واحد | التحقق العملي |
| Parallel Run | تشغيل متوازٍ مع النظام القديم فترة | مقارنة النتائج |
| Full Cutover | تحويل كامل بعد قبول UAT | الاعتماد النهائي |
- **بوابات الميزات (Feature Flags):** تفعيل الوحدات تدريجياً دون نشر جديد.
- **الأرصدة الافتتاحية المالية:** تُدخَل كقيود افتتاحية بتاريخ التحويل.

## 4. الاستمرارية والتعافي من الكوارث (Backup & DR)

### 4.1 الأهداف بالأرقام
| المؤشر | الهدف |
|--------|-------|
| **RPO** (أقصى فقدان بيانات مقبول) | **≤ 15 دقيقة** |
| **RTO** (أقصى زمن للاستعادة) | **≤ 1 ساعة** |
| **الاحتفاظ (Retention)** | يومي 30 يوماً · أسبوعي 12 أسبوعاً · شهري 12 شهراً · سنوي 7 سنوات (متطلب قانوني) |
| **توافر النظام (Uptime)** | ≥ 99.5% (≈ 3.6 ساعة توقف/شهر كحد أقصى) |

### 4.2 آلية النسخ الاحتياطي
| المكوّن | الاستراتيجية | التكرار |
|---------|--------------|---------|
| PostgreSQL | نسخة كاملة + **WAL مستمر (PITR)** | كامل يومي + WAL كل بضع دقائق |
| S3/MinIO (المستندات) | **Versioning** + مزامنة لموقع/منطقة ثانية | لحظي |
| Redis | AOF (البيانات قابلة لإعادة البناء أساساً) | مستمر |
| الإعدادات/الأسرار | نسخ مشفّرة منفصلة (Vault) | عند التغيير |

- **قاعدة 3-2-1:** 3 نسخ، على وسيطين، إحداها **خارج الموقع (Off-site)**.
- **تشفير النسخ** أثناء النقل والتخزين.
- **اختبار الاستعادة الدوري:** استعادة كاملة تجريبية **شهرياً** للتحقق من صلاحية النسخ وقياس RTO الفعلي.

### 4.3 سيناريوهات التعافي
| السيناريو | الإجراء | RTO المستهدف |
|-----------|---------|:-----------:|
| حذف بيانات خاطئ | استعادة نقطة زمنية (PITR) لما قبل الحذف | ≤ 30 دقيقة |
| تلف قاعدة البيانات | التبديل لنسخة/Replica + استعادة WAL | ≤ 1 ساعة |
| فقد الخادم بالكامل | إعادة النشر من Docker/IaC + استعادة البيانات | ≤ 1 ساعة |
| كارثة الموقع | التحويل للموقع الثانوي (Off-site) | ≤ 2 ساعة |
| فدية/اختراق | العزل + الاستعادة من نسخة نظيفة سابقة للاختراق | حسب الحادث |

### 4.4 استمرارية التشغيل
- **مراقبة استباقية:** Prometheus/Grafana + Sentry + تنبيهات على (فشل النسخ، امتلاء القرص، توقف Worker، جهاز بصمة Offline).
- **Runbooks:** إجراءات موثّقة لكل سيناريو تعافٍ يتبعها فريق التشغيل خطوة بخطوة.
- **البنية ككود (IaC):** Docker/Compose (وKubernetes مستقبلاً) لإعادة بناء البيئة بسرعة وبشكل متكرر.
