# Backlog — بنود مؤجّلة موثّقة (لا تُنفّذ إلا بقرار Lead Architect)

يوثّق هذا الملف قدرات مطلوبة أو ديونًا تقنية معروفة اكتُشفت أثناء المراجعات، دون
تنفيذها الآن — حفاظًا على قاعدة «لا كسر لموجود، ولا Business Logic جديد خارج النطاق».

---

## Payroll — فجوات خلفية تمنع عمليات واجهة مطلوبة

اكتُشفت في Payroll Architecture Review (Phase 2 · Discovery). المحرّك الخلفي لا
يكشف نهايات API لهذه العمليات، فلا يمكن بناؤها كواجهة فوق موجود. تتطلّب وحدةً خلفيةً
جديدةً (منطق + اختبارات) — خارج نطاق «واجهة فوق المحرّك».

- **Payroll Periods — تعديل / إغلاق / إعادة فتح / أرشفة:** حالة الفترة
  (`PayrollPeriod::STATUSES`) خاملة؛ لا كود يغيّرها ولا نهاية API. الموجود: إنشاء + عرض فقط.
- **Payroll Run — إلغاء (Cancel) / إعادة فتح / فكّ قفل:** الانتقالات الوحيدة
  `draft|processing → approved → locked`. لا cancel/reopen/unlock. الحالتان
  `completed`/`paid` معلنتان لكن ميتتان (لا كود يعيّنهما).
- **Payslip — PDF / إعادة توليد (Regenerate):** يوجد HTML للطباعة فقط (لا مكتبة PDF)،
  ولا نهاية regenerate (الكشف مشتقّ من `payroll_item` المجمّد).
- **Salary Component — حذف نهائي (Hard delete):** المتاح تعطيل (`is_active=false`)
  عبر التحديث فقط؛ لا حذف فعلي (لحماية المراجع التاريخية).

## Payroll — ديون تقنية خلفية كامنة (تصليب مؤجّل)

مخاطر لا تُشكّل ثغرة API حاليًّا لكنها تستحق تصليبًا لاحقًا (قرار: توثيق فقط الآن):

1. **snapshot غير إلزامي قبل calculate:** `calculateRun` يعمل بلا لقطة حضور/إجازات
   وينتج راتبًا أساسيًّا فقط **بصمت** (بلا خصم غياب/تأخير/إجازة غير مدفوعة). لا حارس
   ترتيب في الخلفية. — تُعالَج تجربةُ المستخدم في الواجهة بترتيب snapshot→calculate،
   لكن الحارس الخلفي يبقى دَينًا.
2. **غياب قفل صفوف (lockForUpdate):** approve/lock/calculate = read-check-then-update
   بلا قفل صف → سباق TOCTOU نظري عند التزامن.
3. **دوال عامة بلا حارس حالة:** `calculateEmployee` / `snapshotEmployee` (المفردة)
   `public` بلا فحص حالة المسير — غير قابلة للوصول عبر API الآن، لكنها فخّ مستقبلي.
4. **حساب بأرقام float:** `PayrollCalculationService` يحسب بـ`float` + `round(2)`
   لكل سطر (لا سنتات صحيحة/BCMath) → انجراف تقريب محتمل عبر آلاف السطور.
5. **status column comment** في `payroll_runs` يُغفل `locked` (تجميلي).
6. **تعدّد المسيرات لكل فترة:** لا حارس يمنع إنشاء عدّة runs لنفس الفترة (سؤال تصميمي).

## Legal — فجوات خلفية في محتوى القضية (Phase 3 · PR-5)

اكتُشفت أثناء بناء واجهة محتوى القضية (وثائق/أطراف/خط زمني/أرشيف). الواجهة تعكس
هذه القيود ولا تحاول تجاوزها؛ رفعها يتطلّب عملًا خلفيًّا (منطق + اختبارات):

- **الوثائق — رفع الملف الفعلي (File Upload):** `case_documents` تسجّل بيانات وصفية
  فقط (`storage_disk`/`storage_path` = metadata، «لا رفع فعلي» في المهاجرة). لا نهاية
  رفع/تنزيل/معاينة ملف. المتاح: إنشاء metadata + عرض + حذف.
- **الوثائق — تعديل (Update):** لا نهاية `PUT documents/{id}`؛ المتاح إنشاء وحذف فقط.
- **الأطراف — تعديل / حذف:** `CasePartyController` يكشف `index`/`store` فقط؛ لا
  `update`/`destroy`. المتاح: إضافة + عرض فقط.
- **الخط الزمني — Append-only بحكم التصميم:** لا نهاية تعديل/حذف لأي حدث (سجل قانوني
  دائم). ليست فجوةً بل قرار تصميمي مقصود — موثّق هنا للوضوح.

## Legal — فجوات في المهام والإنجاز اليومي (Phase 3 · PR-6)

اكتُشفت أثناء بناء إشراف المهام وسجل الأعمال. الواجهة تعكس المتاح فقط:

- **المهام — حذف (Delete):** `TaskController` يكشف index/show/store/update/assign/complete
  فقط؛ لا `destroy`. المهمة تُنجَز (done) ولا تُحذف — لا زر حذف في الواجهة.
- **المهام — حالات وسيطة:** `CaseTask::STATUSES = ['open','done']` فقط؛ لا "قيد التنفيذ".
  الواجهة لا تعرض حالات غير موجودة.
- **الإنجاز اليومي — تعديل/حذف من الإدارة:** `GET /worklog` اطّلاعي فقط (view_all)؛
  لا نهاية تعديل/حذف للمشرف. التسجيل ذاتي لليوم فقط في بوابة المحامي (upsert).
