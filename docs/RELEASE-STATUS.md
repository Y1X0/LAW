## Backup & Restore — إغلاق Phase 13 · B1 (Production Ready)

أوّل حاصرة تسليم: نسخ احتياطي موثوق لقاعدة البيانات مستقلّ عن المزوّد وبيد Owner — يحوّل النظام
من «برنامج يعمل» إلى «نظام شركة يمكن الاعتماد عليه». بُني على PRات صغيرة (CI أخضر، دمج بموافقة).

**المحرّك:** `BackupService` يفرّغ Postgres عبر `pg_dump -Fc` → يرفع إلى **قرص `backups` (دلو R2
منفصل عن الوثائق — عزل أمني)** → يسجّل ويدقّق → يقلّم الاحتفاظ **GFS** (يومي 30/أسبوعي 12/شهري
12/يدوي 30). التفريغ خلف عقد `DatabaseDumper` (قابل للاختبار).

**الجدولة:** خدمة Cron في Render (`law-backup`) تشغّل `backup:run` يوميّاً؛ النوع يُشتقّ من التاريخ.

**واجهة Owner:** الإعدادات → النسخ الاحتياطي — آخر نسخة ناجحة + «إنشاء الآن» + جدول بالتنزيل،
تحت `backup.manage`. **لا استعادة/حذف من الواجهة** (قرار أمان).

**الاستعادة (CLI فقط):** `php artisan backup:restore <id> --force` — عملية مدمِّرة مُحصَّنة (تأكيد
إجباري) عبر `pg_restore`، مُدقَّقة (`backup_restored`). الوثائق تبقى على R2 (لم تتأثّر).

**الإثبات الحيّ (دليل التسليم):** سير عمل **Backup Restore Integration** يشغّل دورة كاملة على
Postgres حقيقي — **نسخ → إضافة بيانات → حذف → استعادة → تأكّد عودة البيانات** — عبر
`tests/Integration/BackupRestoreLiveTest.php`. الوحدات (`BackupServiceTest`/`BackupApiTest`/
`BackupRestoreCommandTest`) تغطّي التنسيق والصلاحيات والتقليم والتحصين. التفاصيل التشغيلية في
`docs/BACKUP-RUNBOOK.md`.

### المؤجَّل (Backlog — ليس أخطاء)

نسخ ملفات R2 كاملة (تُكتفى بدوام التخزين الكائني + Versioning)، تشفير النسخ بمفتاح إضافي (GPG)،

## Email (SMTP) — إغلاق Phase 13 · B2 (Production Ready)

ثاني حاصرة تسليم: قناة بريد فعليّة للمكتب — تُخرِج رسائل النظام من «log» إلى صندوق بريد المستخدم.
بُنيت على 3 PRات صغيرة (Discovery-first، CI أخضر، دمج بموافقة)، مستقلّة عن أي مزوّد (أي خادم SMTP).

**PR-1 · استعادة كلمة المرور (واجهة):** صفحتا «نسيت كلمة المرور؟» و«تعيين كلمة مرور جديدة» عامّتان
(خارج الحماية)، موصولتان بمسار Laravel القياسي (`forgot-password` / `reset-password`) عبر إشعار
`ResetPassword` على قناة `mail`. رابط الاستعادة يوجّه إلى `/reset-password` بالواجهة.

**PR-2 · تفعيل SMTP الحقيقي:** `MAIL_*` أسرار `sync:false` في `render.yaml` (فارغ ⇒ يعود إلى `log`،
آمن قبل الضبط)؛ الإرسال متزامن (`QUEUE_CONNECTION=sync`، لا عامل طابور). التوثيق التشغيلي في
`docs/DEPLOY-RENDER.md` («تفعيل البريد (SMTP)»).

**PR-3 · قناة بريد الإشعارات:** نفس مسار الإشعارات الوحيد (`emit`) يُرسِل الآن نسخة بريدية **بعد**
كتابة الإشعار الداخلي، محكومة بثلاثة شروط: (1) نوع الإشعار ضمن **قائمة بيضاء بالإعداد**
(`config/notifications.php` → `email_types`: تذكيرات الجلسات/الفواتير + قرارات الإجازة؛ المهام تبقى
داخل النظام فقط لتفادي إغراق البريد)، (2) المستخدم **نشط** (`status = active`)، (3) بريده **غير فارغ**.
البريد **أثرٌ جانبي best-effort**: أي فشل (SMTP معطّل، مستخدم محذوف) يُسجَّل تحذيراً فقط ولا يكسر
الطلب، والإشعار الداخلي (مصدر الحقيقة) يُنشأ **دائماً** أيّاً كانت نتيجة البريد. قالب `NotificationMail`
RTL بسيط يعكس عنوان/نصّ الإشعار. تعديل القائمة البيضاء لا يحتاج تغيير كود.

**الإثبات:** `NotificationEmailTest` (5) يؤكّد: أنواع القائمة البيضاء تُرسَل لمستخدم نشط (كلها)،
المهام لا تُرسَل، غير النشط لا يُراسَل، الفارغ البريد لا يُراسَل — **ومع ذلك يُنشأ الإشعار الداخلي في
كل حالة**. `PasswordResetTest` يغطّي مسار الاستعادة طرفاً لطرف (بما فيه `Notification::fake`).
المجموعة الخلفية (718) خضراء بلا تراجع. الإرسال الحقيقي يُثبَت في الإنتاج بضبط أسرار `MAIL_*`
(لا يمكن إثباته في CI بلا خادم SMTP — CI يستخدم `array`/`Mail::fake`).

### المؤجَّل (Backlog — ليس أخطاء)

تفضيلات بريد لكل مستخدم (اشتراك/إلغاء لكل نوع)، قوالب بريد قابلة للتخصيص من الواجهة، ودفع

## Data Migration Platform — إغلاق Phase 10 + Phase 11 (Production Ready)

منصّة هجرة بيانات موحّدة لاستيراد/تصدير بيانات المكتب من Excel، بُنيت على PRات صغيرة (لكلٍّ
مسؤولية واحدة، CI أخضر، دمج squash بعد موافقة)، على منهجية Discovery-first ومبدأ الأطوار السابقة:
**الاستيراد لا يتجاوز منطق النطاق أبداً** — كل صفّ يمرّ عبر خدمة الكيان لا عبر `Model::create`.

**المبدأ المعماري الجوهري (SEC — لا التفاف على النطاق):** كل مستورد يمرّ كل صفّ عبر خدمة الكيان
(`ClientService` / `CaseService`)، فيحصل الصفّ المستورد على **نفس** التحقّق والتدقيق والإسناد والخط
الزمني الذي يحصل عليه الإدخال اليدوي — لا استيراد يكتب الجداول مباشرة، فلا التفاف على قواعد العمل.

**الدورة الموحّدة لكل كيان:** رفع ملف → **معاينة (dry-run بلا حفظ)** → مطابقة الأعمدة (رأس الملف ←
حقل النظام) → اختيار مفتاح المطابقة (upsert) → تحقّق كل الصفوف → **التزام ذرّي (الكل-أو-لا-شيء)**
عبر `DB::transaction` → تقرير النتائج. صفّ واحد غير صحيح يمنع الحفظ كاملاً — **لا استيراد جزئي**.

**المنصّة (مصدر الحقيقة الوحيد):** سِجلّ `DataImportService::IMPORTERS` بالخادم يُعلِن الكيانات القابلة
للاستيراد؛ نقطة `GET /admin/data/import/manifest` تعيدها **مصفّاة بصلاحيّات المستخدم**، والواجهة
تبني قائمة الأنواع وسير العمل ديناميكياً منها. إضافة مستورد مستقبلاً = تسجيل سطر + مسارَي
preview/commit، فيظهر تلقائياً في مركز الهجرة دون تعديل الواجهة — ولا يُعرض كيان لا يملك المستخدم
صلاحية استيراده.

**العملاء (Phase 10):** استيراد عبر `ClientService` بمفتاح مطابقة **قابل للاختيار**
(`national_id / email / name`)، مع **مطابقة أعمدة** خادميّة (رؤوس عربية اعتباطية ← حقول النظام).

**القضايا (Phase 11):** استيراد عبر `CaseService` بمفتاح `internal_number` (مطلوب + فريد):
- **ربط العميل** بلا تخمين: `client_national_id` ثم `client_name` — خطأ صفّ عند 0 أو أكثر من تطابق.
- **ربط المحامي** بالأولوية: `lawyer_employee_no` ثم `lawyer_national_id` ثم `lawyer_name`؛ فارغ =
  بلا محامٍ (صحيح)، موجود-وغير-موجود = خطأ صفّ.
- **خط زمني صادق:** هجرة قضية قديمة تُسجَّل «تم استيراد القضية من النظام السابق» لا «تم إنشاء
  القضية» (معامل `origin` متوافق خلفياً)؛ `opened_date` يبقى تاريخ الفتح القانوني. **صفر إشعارات**
  عند الاستيراد (مؤكَّد) — فلا إغراق للمحامين عند تحميل بيانات تاريخية.
- **رفض تكرار `internal_number` داخل الملف** برسالة نظيفة (يتفادى انتهاك قيد التفرّد → 500).

**الحوكمة (RBAC):** كل استيراد محميّ بصلاحية إنشاء الكيان نفسها (`clients.create` / `cases.create` /
`employees.create`) — **لا صلاحية ولا هجرة جديدة**. الحقول المالية للموظفين تُطبَّق فقط لمن يملك
`employees.salary.view` (اتّساقاً مع عزل الرواتب). التصفية server-side فالواجهة لا تكشف ما لا يُنفَّذ.

**الإثبات:** `ClientImportTest` (7) · `CaseImportTest` (11: معاينة/التزام، ذرّية، صلاحية 403، ربط
العميل/المحامي وأخطاؤهما، مطابقة أعمدة عربية، حدث الاستيراد لا الإنشاء + بقاء `opened_date`، رفض
التكرار داخل الملف) · `ImportManifestTest` (4: مصفّى بالصلاحية، القائمة الكاملة، فارغ بلا صلاحية،
401) · `DataImportTest`/`DataExportTest` (الموظفون + التصدير) · `AdminDataPage.test` (المنصّة الديناميكية
+ ظهور القضايا + حالة «لا صلاحية»). المجموعة الخلفية (674) والواجهة (259) وE2E خضراء بلا تراجع.

## Financial / Invoicing — إغلاق Phase 6 (Production Ready)

طور مالي كامل بُني على 11 PR صغيراً (لكلٍّ مسؤولية واحدة، CI أخضر، دمج squash بعد موافقة):

**الأساس المحاسبي:** دليل حسابات (`chart_of_accounts`) مع **محلّل بالدور** (`AccountResolver`) لا
بالرقم؛ **محرّك قيد مزدوج** يفرض التوازن (مدين=دائن) داخل الخدمة، ترحيلاً ذرّياً، ومناعةً بعد
الترحيل (تصحيح بالعكس لا الحذف).

**الدورة التشغيلية الكاملة:** فاتورة (ضريبة لكل بند + خصم، اعتماد يولّد قيد إيراد آليّاً) →
تحصيل (سند قبض بـ Idempotency، عكس لا حذف، تحديث حالة الفاتورة) → مصروف (سند صرف، عزل
القضية عند الربط، عكس لا حذف) → تقارير (ميزان مراجعة متوازن، مستحقات، أرباح/خسائر) + ملخّص
مالي للعميل (عرض 360°).

**مبادئ محفوظة عبر الطور:** لا حساب مالي في الواجهة (كل المبالغ من الـAPI)؛ الأزرار تظهر
بالقدرة والخادم الحكم النهائي؛ لا `branch_id` (تعدّد الفروع مؤجَّل)؛ دور «المالية» (accountant)
موصول بالمجال المالي في RBAC.

**الإثبات (End-to-End):** `FinancialJourneyTest` يشغّل الرحلة كاملة بدور المحاسب عبر الـAPI
(فاتورة → اعتماد → قيد → تحصيل → مصروف → تقارير + ملخّص) وتتّسق أرقامها: ميزان متوازن
1600=1600، مستحقات 600، صافي أرباح 800. المجموعة الخلفية الكاملة والواجهة خضراء بلا تراجع.

## Notifications / Reminders — إغلاق Phase 8 (Production Ready)

نظام إشعارات داخل النظام + محرّك تذكيرات زمنية، بُني على 5 PRات صغيرة (Discovery-first، CI أخضر،
دمج squash بعد موافقة)، على مبادئ الأطوار السابقة: الخادم مصدر الحقيقة والواجهة طبقة عرض.

**الرحلة الكاملة (مُراجَعة طرفاً لطرف):**

```
حدث مجال (اعتماد إجازة / إسناد مهمة …)        الأمر notifications:remind (Render cron)
        ↓                                              ↓
NotificationService::emit  ← المصدر الوحيد →   ReminderService (قراءة فقط، مانع تكرار)
        ↓                                              ↓
        └──────────────→ جدول user_notifications ←─────┘
                                ↓
                   API (/notifications*، خلف notifications.view_own)
                                ↓
                   مركز الإشعارات في رأس Shell (جرس + عدّاد + قائمة)
```

- **PR-1:** الأساس — جدول `user_notifications`، `NotificationService::emit` (مصدر وحيد)، نقاط API
  ذاتية + `notifications.view_own`.
- **PR-2:** مُطلِقات الأحداث بجوار `recordAudit` (قرار الإجازة → مقدّمها؛ إسناد/إكمال المهمة →
  المُسنَد إليه/مُنشئها) — لا إشعار ذاتي، ولا مستلِم بلا حساب.
- **PR-3:** مركز الإشعارات (جرس + عدّاد غير مقروء من الخادم + قائمة + فلتر + تعليم كمقروء).
- **PR-4:** محرّك التذكيرات (جلسات قادمة → محامو القضية؛ فواتير تقترب/تجاوزت → معتمِدها).
- **PR-5:** هذه المراجعة والإغلاق.

**RBAC والعزل:** صلاحية واحدة `notifications.view_own` (لكل الأدوار)؛ كل نقطة منطوقة على المستخدم
الحالي — إشعار الغير يُعاد 404 (لا يُكشف وجوده). لا صلاحيات في الواجهة؛ الخادم الحكم.

**منع التكرار (نوعان):** أحداث لحظية — العمليات الـ idempotent لا تُنتج تكراراً (اعتماد ثانٍ مرفوض
قبل الإطلاق). تذكيرات زمنية — فحص وجود صفّ `(user, type, related)` قبل كل تذكير، فتشغيل cron
مراراً لا يضخّم الجدول.

**الأداء:** التذكيرات تعمل على **مجموعة مرشّحين محدودة بالنافذة** (جلسات خلال 3 أيام + فواتير
مستحقّة/متأخّرة)، مع `with('case.assignments')` لتفادي N+1 على القضية/الإسناد؛ العمل لكل مرشّح
ثابت الاستعلامات — **لا N+1 غير محدود**.

**الصمود:** الإطلاق عبر `NotifiesUsers` (best-effort) — فشل إشعار يُسجَّل ولا يكسر العملية الأساسية
ولا يوقف بقية معالجة التذكيرات (مُثبَت باختبارات).

### تفعيل التذكيرات في الإنتاج (خطوة تشغيل — قطعة البنية المتبقّية)

الأمر مُجدوَل في `routes/console.php` يوميّاً (`notifications:remind` عبر `dailyAt('06:00')`)، لكنه
**خامل حتى يُشغَّل `php artisan schedule:run` دوريّاً**. لتفعيله في Render:

1. أضِف خدمة **Cron Job** في `render.yaml` (أو لوحة Render) تُشغّل `php artisan schedule:run` كل دقيقة
   على نفس صورة الـ backend وبيئته/قاعدته.
2. لا أسرار جديدة؛ يكفي وصول القاعدة نفسه.
3. الأمر قابل للتشغيل يدويّاً في أي وقت (`php artisan notifications:remind`) — آمن ومانع للتكرار.

> إلى أن تُضاف خدمة الـ cron، تبقى الإشعارات اللحظية (الأحداث) عاملة بالكامل؛ التذكيرات الزمنية
> تنتظر مُشغّل الجدولة فقط.

## Document Management — إثبات التحقّق الحيّ (Phase 5 مُغلَقة)

العمل البرمجي مكتمل ومُتحقَّق منه في CI (الطبقتان Frontend + Backend، الأمان، معالجة
الفشل، الاختبارات خضراء، Backlog نظيف). اختبارات CI الرئيسية تستخدم `Storage::fake('r2')`،
وهي وحدها **لا تُثبت** الاتصال الفعلي بـ R2. لذا أُجري تحقّق حيّ مخصّص على **Cloudflare R2 الحقيقي**:

- **السير:** `R2 Integration` · التشغيل رقم 2 (`workflow_dispatch`) على `main` — **نجح**.
- **النتيجة:** `OK (1 test, 6 assertions)` — الاختبار **نُفِّذ** (لم يُتخطَّ)، والأسرار الخمسة حُقنت من GitHub Secrets.
- **ما أُثبت فعليّاً:** رفع ملف 256KB إلى R2 → تأكيد الوجود → مطابقة الحجم → تنزيل → **مطابقة SHA-256 مع الأصل** → حذف → تأكيد الحذف.

بهذا تحقّق الاتصال الفعلي، وصلاحية المفاتيح، وسياسات الـ Bucket، وسلامة الجولة عبر الشبكة —
وهي بالضبط النقاط التي لم يكن CI الرئيسي يستطيع إثباتها. الحالة الآن **Production Ready**.

---

## المتطلّبات قبل التحقّق الحيّ

1. إنشاء دلو (Bucket) في Cloudflare R2 ومفاتيح API له.
2. ضبط أسرار البيئة في Render (Environment):
   - `R2_ACCESS_KEY_ID`
   - `R2_SECRET_ACCESS_KEY`
   - `R2_BUCKET`
   - `R2_ENDPOINT`
   - `R2_DEFAULT_REGION=auto`
   - `LEGAL_DOCUMENTS_DISK=r2` (مضبوط أصلاً في `render.yaml`)
3. القرص `r2` معرّف في `backend/config/filesystems.php` (private · path-style · throw).

> الأسماء موثّقة في `backend/.env.example`. لا تُوضع القيم الحسّاسة في المستودع.

## التحقّق الآلي عبر CI (R2 Integration workflow)

بدل الاعتماد على جولة يدوية فقط، يوجد الآن سير عمل مخصّص يختبر R2 **الحقيقي** آليّاً:

- **الملف:** `.github/workflows/r2-integration.yml` · **الاختبار:** `backend/tests/Integration/R2LiveTest.php`.
- **يغطّي:** رفع ملف 256KB → تأكيد الوجود والحجم → تنزيل → **مطابقة SHA-256** → حذف → تأكيد الحذف. أي فشل في أي خطوة يُفشل السير.
- **يُشغَّل:** يدويّاً (`workflow_dispatch`)، وعند دفع تغييرات تمسّ التخزين إلى `main`.
- **معزول عن CI الرئيسي:** الاختبار ليس ضمن مجموعتَي Unit/Feature، فلا يعمل في `php artisan test` ولا يتطلّب أسراراً هناك.
- **بدون أسرار:** يتخطّى الاختبار برسالة واضحة (السير يبقى أخضر) — لا يُخزَّن أي مفتاح في المستودع.

### GitHub Secrets المطلوبة (على مالك المستودع)

في **Settings → Secrets and variables → Actions → New repository secret** أضِف:

| Secret | مثال/ملاحظة |
|--------|-------------|
| `R2_ACCESS_KEY_ID` | من لوحة Cloudflare R2 API Tokens |
| `R2_SECRET_ACCESS_KEY` | السرّ المقابل |
| `R2_BUCKET` | اسم الدلو |
| `R2_ENDPOINT` | `https://<account_id>.r2.cloudflarestorage.com` |
| `R2_DEFAULT_REGION` | `auto` |

> هذه أسرار CI منفصلة عن أسرار Render (المذكورة أعلاه)، لكن قيمها نفسها.

بعد ضبط الأسرار، شغّل السير من تبويب **Actions → R2 Integration → Run workflow**. نجاحه = إثبات التكامل الحيّ.
