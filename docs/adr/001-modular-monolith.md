# ADR-001: اعتماد Modular Monolith بدل Microservices

- **Status:** معتمَد
- **التاريخ:** 2026-07-28

## Context (السياق)
مكتب المحاماة يبدأ بـ 10 موظفين مع نية التوسع. نحتاج معمارية تعطي **سرعة تطوير عالية** و**حدود وحدات واضحة** دون تحميل فريق صغير عبء التشغيل الموزّع المبكر (شبكة داخلية، توزيع المعاملات، مراقبة موزّعة، اتساق نهائي). في الوقت نفسه يجب ألا نحبس أنفسنا في تصميم يصعب تفكيكه لاحقاً عند النمو.

## Decision (القرار)
نعتمد **Modular Monolith**: تطبيق واحد قابل للنشر، منظّم داخلياً إلى وحدات (Modules) مستقلة منطقياً بحدود صريحة (HR, Cases, Finance, Attendance, Marketing, Notifications, Documents). كل وحدة تملك جداولها وخدماتها وتتواصل مع غيرها عبر واجهات/أحداث معرّفة لا عبر الوصول المباشر لجداول وحدة أخرى (انظر [module-boundaries](../module-boundaries.md)).

## Alternatives Considered (البدائل)
| البديل | سبب الرفض |
|--------|-----------|
| **Microservices من البداية** | تعقيد تشغيلي غير مبرر لفريق/حجم صغير؛ توزيع المعاملات المالية معقّد؛ تكلفة بنية تحتية أعلى |
| **Monolith تقليدي (بلا وحدات)** | يتحلّل بمرور الوقت إلى تشابك (Big Ball of Mud) ويصعب تقسيمه لاحقاً |
| **Serverless Functions** | غير ملائم لنظام معاملاتي مترابط بعلاقات قاعدة بيانات قوية |

## Consequences (النتائج)
**إيجابيات:** بساطة النشر والتطوير، معاملات محلية قوية (ACID) مهمة للمالية، حدود واضحة تتيح العمل المتوازي، مسار ترقية سلس.
**سلبيات/مقايضات:** التوسع يكون للتطبيق ككل (نخفّفه بـ Stateless + Load Balancer + Read Replicas)؛ يتطلب انضباطاً لمنع اختراق حدود الوحدات (يُفرَض بالمراجعة و module-boundaries).

## When to Revisit (متى يُعاد النظر)
عند ظهور **مؤشرات قياس** واضحة:
- وحدة بعينها (مثل الأرشفة أو التقارير أو الإشعارات) تستهلك موارد/تتوسّع بمعدل يختلف جوهرياً عن الباقي.
- تجاوز ~100–150 مستخدماً متزامناً بأحمال غير متجانسة.
- الحاجة لدورات إصدار مستقلة لوحدة معينة.
عندها تُفصَل الوحدة الأثقل أولاً كخدمة مستقلة (Strangler Pattern)، مستفيدين من الحدود المعرّفة مسبقاً.
