# ADR-003: نمط Adapter لتكامل أجهزة البصمة

- **Status:** معتمَد
- **التاريخ:** 2026-07-28

## Context (السياق)
يجب دعم أجهزة بصمة من مورّدين مختلفين (**ZKTeco, Hikvision, Suprema, Anviz**)، ولكل مورّد بروتوكول/SDK/API مختلف (Push ADMS، ISAPI، BioStar REST، CrossChex/TCP). نريد ألا يتأثر جوهر النظام بنوع الجهاز، ودعم إضافة أجهزة جديدة مستقبلاً دون تعديل منطق الحضور.

## Decision (القرار)
نعتمد **نمط المحوّل (Adapter Pattern)**: واجهة موحّدة `BiometricAdapter` (connect / fetchLogs / parseWebhook / normalize / enrollUser / getDeviceStatus)، يطبّقها محوّل مستقل لكل مورّد. تُكتب كل سجلات البصمة في طبقة **Staging خام** (`attendance_logs`) قبل معالجتها إلى `attendance_records`، بغضّ النظر عن مصدرها.

## Alternatives Considered (البدائل)
| البديل | سبب الرفض |
|--------|-----------|
| **تكامل مباشر مع كل جهاز في منطق الحضور** | يشابك الكود بتفاصيل كل مورّد ويجعل إضافة جهاز جديد مكلفة وهشّة |
| **الاعتماد على مورّد واحد فقط** | يقيّد المكتب ويمنع استخدام الأجهزة القائمة |
| **وسيط سحابي حصري (Cloud only)** | يفرض اتصالاً دائماً بالإنترنت ويزيد التبعية الخارجية |

## Consequences (النتائج)
**إيجابيات:** عزل تام لتفاصيل المورّد، إضافة جهاز جديد = محوّل جديد فقط، اختبار كل محوّل بمعزل، دعم Push + Pull معاً. طبقة Staging تضمن **عدم فقدان أي بصمة** حتى لو تعذّرت مطابقة الموظف فوراً.
**سلبيات/مقايضات:** كتابة/صيانة محوّل لكل مورّد؛ اختلاف قدرات الأجهزة (بعضها لا يدعم Push) يعالَج بمزيج Push أساسي + Pull للتسوية.

## When to Revisit (متى يُعاد النظر)
عند توحّد السوق على بروتوكول قياسي واحد، أو تبنّي المكتب مورّداً واحداً حصرياً على المدى الطويل، أو ظهور منصة وسيطة موثوقة تغطي كل الأجهزة بواجهة واحدة.
