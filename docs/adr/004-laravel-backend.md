# ADR-004: اعتماد Laravel 11 للـ Backend

- **Status:** معتمَد
- **التاريخ:** 2026-07-28

## Context (السياق)
نحتاج إطار عمل خلفي يوفّر **إنتاجية عالية** لفريق متوسط، ويأتي بمكوّنات جاهزة نحتاجها فعلاً (ORM، طوابير، مجدول، بث لحظي، صلاحيات، تدقيق)، مع مجتمع ووثائق قوية وتوظيف ميسور محلياً، ومعمارية **API-First** تسمح لاحقاً بتطبيق جوّال وبوابة عملاء على نفس الـ API.

## Decision (القرار)
نعتمد **Laravel 11 (PHP 8.3)** كإطار الـ Backend، مع: Sanctum/Passport (JWT)، spatie/laravel-permission (RBAC) + Policies (ABAC)، Queue + Horizon (Redis)، Reverb (WebSocket)، Scout + Meilisearch، laravel-auditing.

## Alternatives Considered (البدائل)
| البديل | التقييم |
|--------|---------|
| **ASP.NET Core 8** | أداء ممتاز وقوي للمؤسسات، لكنه يرفع تكلفة/تعقيد البيئة ويقلّل توفّر الكفاءات محلياً مقارنة بـ PHP |
| **NestJS (Node.js/TS)** | يوحّد اللغة مع الـ Frontend، لكن يتطلب تجميع مكوّنات أكثر يدوياً (ORM/Queue/Realtime) مقابل جاهزيتها في Laravel |
| **Django (Python)** | ناضج، لكن نظام الطوابير/البث/الصلاحيات يحتاج تجميعاً إضافياً |

## Consequences (النتائج)
**إيجابيات:** سرعة تسليم عالية، مكوّنات مؤسسية جاهزة تقلّل الكود المخصّص، توظيف أسهل، مجتمع عربي واسع.
**سلبيات/مقايضات:** أداء PHP الخام أقل من .NET/Go تحت أحمال ضخمة جداً (غير ذي أثر في نطاقنا؛ يُخفَّف بـ Caching/Queue/Replicas)؛ لغة مختلفة عن الـ Frontend (مقبول مقابل الإنتاجية).

## When to Revisit (متى يُعاد النظر)
إذا تحوّل النظام لـ SaaS واسع بأحمال عالية تتطلب أداءً خاماً أعلى لخدمات محدّدة، تُفصَل تلك الخدمة بلغة/إطار أنسب (بفضل حدود الوحدات ومعمارية API-First) دون إعادة كتابة النظام كله. **قرار الـ Backend محايد عن التصميم** لأن كل شيء يمرّ عبر REST API موثّق.
