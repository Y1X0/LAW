# ADR-005: استراتيجية العزل — Branch الآن، Tenant مستقبلاً

- **Status:** معتمَد
- **التاريخ:** 2026-07-28

## Context (السياق)
النظام يبدأ لمكتب واحد بعدة فروع محتملة، مع نية مستقبلية محتملة لتحويله إلى منتج **SaaS** يخدم عدة مكاتب. كان هناك غموض في التوثيق (ذكر `branch_id / tenant_id` معاً) بينما الجداول الفعلية تستخدم `branch_id` فقط. يجب حسم هذا الغموض لمنع تضخم التصميم من جهة، وحبس مسار SaaS من جهة أخرى.

## Decision (القرار)
**المرحلة الحالية: عزل قائم على الفرع (Branch-based Isolation).**
- كل الكيانات التشغيلية تحمل `branch_id` فقط كحد عزل تشغيلي.
- **لا يُضاف `tenant_id` إلى الـ 65 جدولاً الآن** (تجنّباً للتعقيد المبكر — Over-Engineering).
- الهرم التنظيمي الحالي:
```
company (سجل واحد ضمن settings/branches)
 └── branches
      └── departments · users · employees · cases · attendance · invoices ...
```

**الجاهزية المستقبلية لـ SaaS (Tenant-based):**
عند التحول لـ SaaS، يُدخَل `tenant_id` كطبقة عزل **أعلى** من الفرع دون إعادة تصميم جذري:
```
tenants
 └── companies
       └── branches
             └── (باقي الكيانات)
```
والانتقال يتم عبر أحد مسارين نُبقيهما مفتوحين:
1. **`tenant_id` على الجداول** (Shared DB, Shared Schema) + فرضه عبر Global Scope تلقائي + تعزيزه بـ **PostgreSQL RLS**.
2. **Schema/DB لكل مستأجر** (عزل أقوى) — ممكن لأن الوصول للبيانات مركزيّ عبر طبقة Repository.

## Alternatives Considered (البدائل)
| البديل | سبب الرفض الآن |
|--------|-----------------|
| **إضافة `tenant_id` لكل جدول فوراً** | تعقيد وتكلفة بلا حاجة حالية (مكتب واحد)؛ يبطئ MVP |
| **تجاهل SaaS تماماً** | يغلق باب توسّع تجاري محتمل ويجعل الانتقال لاحقاً مكلفاً |
| **DB منفصلة لكل فرع الآن** | مبالغة؛ الفروع تشترك في نفس المكتب وتحتاج تقارير موحّدة |

## قواعد التصميم لضمان الجاهزية (دون تنفيذ مبكر)
- كل وصول للبيانات يمرّ عبر **طبقة Repository/Service** (لا استعلامات مبعثرة) لتسهيل حقن العزل لاحقاً.
- استخدام **Global Query Scope** لفلترة `branch_id` تلقائياً؛ نفس الآلية ستحقن `tenant_id` مستقبلاً.
- عدم افتراض تفرّد المعرّفات عبر المكاتب في منطق الأعمال إلا حيث يلزم.

## Consequences (النتائج)
**إيجابيات:** MVP أبسط وأسرع، تصميم نظيف الآن، ومسار SaaS محفوظ بتكلفة انتقال محدودة (إضافة عمود + Scope + RLS).
**سلبيات/مقايضات:** تحويل SaaS لاحقاً يتطلب Migration مدروسة (إضافة `tenant_id` + ترحيل بيانات المكتب الحالي كمستأجر افتراضي) — مقبول ومخطّط له.

## القاعدة التوثيقية المعتمدة
> النظام الحالي يستخدم **`branch_id`** كحدّ عزل تشغيلي. `tenant_id` **غير موجود حالياً** ويُدخَل في مرحلة SaaS كطبقة أعلى دون إعادة تصميم جذري.

## When to Revisit (متى يُعاد النظر)
عند اتخاذ قرار تجاري فعلي بطرح النظام كـ SaaS، أو عند انضمام مكتب ثانٍ مستقل يتطلب عزلاً كاملاً للبيانات.
