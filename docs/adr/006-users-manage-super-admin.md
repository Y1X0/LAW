# ADR-006: اعتبار صلاحية `users.manage` صلاحيةَ مالك المنصّة (Super Admin)

- **Status:** معتمَد
- **التاريخ:** 2026-08-01

## Context (السياق)
كشفت المراجعة الأمنية لمرحلة التثبيت (قبل v1.0) أن صلاحية `users.manage` — التي تحرس إدارة المستخدمين في وحدة تحكّم المنصّة — هي عمليًا **صلاحية عليا (super-permission)**، لسببين بنيويين قائمين منذ RBAC الأصلي (Issue #12):

1. **إسناد الأدوار محاط بـ `users.manage`، لا بـ `roles.manage`.** نقاط `POST/DELETE /api/users/{user}/roles` (وكذلك `role_ids` عند إنشاء مستخدم) داخل مجموعة `permission:users.manage`. لذا يستطيع مالك `users.manage` إسناد **أي دور قائم** — بما فيه دور يمنح `roles.manage` أو `settings.manage` أو `audit.view` أو `users.manage` نفسها — لأي مستخدم بما فيهم نفسه.
2. **إعادة تعيين كلمة المرور الإدارية محاطة بـ `users.manage`.** يستطيع مالكها تعيين كلمة مرور أي حساب (بما فيه حساب أعلى صلاحية) والدخول به.

كِلا المسارين موجودان في العقد الأصلي، و`UserRoleAssignmentTest` يثبت صراحةً أن `users.manage` تكفي لإسناد الأدوار وأن `roles.manage` وحدها **لا** تكفي (403). أي إعادة حِراسة لهذه النقاط تُغيّر عقد مسار قائم وتكسر اختباراته — وهو ما يخالف مبدأ المشروع «ممنوع تغيير سلوك أي API قائم».

## Decision (القرار)
**نعتمد `users.manage` كصلاحية مالك المنصّة الكاملة (Super Admin)، ونوثّق ذلك صراحةً**، بدل محاولة فصل الواجبات بتغيير مسارات قائمة.

هذا يطابق الواقع القائم: الدور النظامي `admin` (المدير العام) يملك **كل** الصلاحيات أصلًا (RbacSeeder)، ووحدة التحكّم الأمامية تُكشَف فقط لمن يملك `roles.manage` عبر الـ probe. المقصود تشغيليًا أن مالك المكتب وحده يحمل هذه الصلاحية.

### قواعد الحوكمة المترتبة
- **لا تُمنَح `users.manage` إلا لدور المالك/المدير العام.** منحها لأي دور آخر = منح تحكّم كامل بالمنصّة.
- طبقات الحماية القائمة تبقى فعّالة: حارس «آخر مدير» (يمنع إسقاط آخر مدير)، منع تعطيل الذات، إبطال الجلسات فورًا عند التعطيل/إعادة كلمة المرور، وتدقيق كامل لكل عملية.

## Alternatives Considered (البدائل)
| البديل | سبب الرفض |
|--------|-----------|
| **فصل الواجبات:** نقل إسناد الأدوار وإعادة كلمة المرور خلف `roles.manage` | يُغيّر سلوك endpoints قائمة ويكسر `UserRoleAssignmentTest` — يخالف قاعدة عدم كسر المسارات القائمة؛ ولا فائدة تشغيلية فعلية لمكتب بمالك واحد |
| **دمج `users.manage` و`roles.manage` في صلاحية واحدة** | تغيير أوسع على نموذج الصلاحيات وبياناته المبذورة؛ يفقد المرونة المستقبلية لفصلهما |
| **تركها بلا توثيق** | تُبقي حدّ `roles.manage` مُضلِّلًا ويُخفي مخاطرة معروفة عن المشغّل |

## Consequences (النتائج)
**إيجابيات:** صفر تغيير على أي مسار قائم؛ توافق كامل مع النموذج المبذور؛ توثيق صريح يزيل الالتباس.
**سلبيات/مقايضات:** لا يوجد فصل واجبات بين «إدارة المستخدمين» و«منح الصلاحيات» — مقبول لحجم مكتب بمالك واحد، ويُعاد النظر عند الحاجة (أدناه).

## When to Revisit (متى يُعاد النظر)
عند الحاجة إلى **أكثر من مستوى إداري** (مثل: مسؤول موارد بشرية يدير المستخدمين دون حق منح صلاحيات النظام)، أو قبل بيع المنصّة لعملاء متعدّدين (multi-tenant) حيث يصبح فصل الواجبات متطلّبًا. عندها تُنقَل نقاط منح الأدوار/إعادة كلمة المرور خلف صلاحية مخصّصة (مثل `roles.grant`) كتغيير مُدار بترحيل صلاحيات وتحديث اختبارات.
